## 2. Detalle por sección

### 2.1 Scripts — sano por ausencia de vector de entrada

`renderScripts()` interpola `s.script_name`/`s.hash`/`s.version` sin escapar (`onclick="toggleScript('${s.script_name}',...)"`). **No es un bug explotable:** `GET /admin/scripts` (`routes/admin.js:194-212`) lee `encrypted_scripts`, poblada **exclusivamente** por `reencrypt_scripts.js` a partir de los nombres de archivo de `backend-server/scripts/` en el filesystem del servidor — cero endpoints HTTP permiten a un usuario nombrar o subir un script. Confirmado por lectura del SELECT (sin `req.body`/`req.query`) y verificado con el harness (§4, punto 5).

### 2.2 Feriados — sano

`motivo` escapado con `escHtml()` (texto) y `escAttr()` (prefill del input), `_feriadosYearFiltro` pasa por `parseInt()`. Coincide con lo que V2b ya había probado en producción con un payload real (`<img src=x onerror=alert(1)>`, sesión 2026-08-24) — no re-testeado con payload nuevo por ser el mismo camino de código sin cambios desde entonces, solo releído.

### 2.3 Métricas — sano, incluido el único vector realmente anónimo del bloque

`renderMetrics()`/`loadLandingAnalytics()` consumen `GET /analytics/data` (`routes/analytics.js`),
cuyos campos `label` y `referrer`→`fuente` **vienen de `POST /analytics/event`, público, sin
autenticación, con `label` de hasta 200 caracteres sin ninguna validación de contenido**
(`routes/analytics.js:14-19`, `label ? String(label).slice(0, 200) : null`). Es el único dato de
este bloque que un atacante externo puede escribir directo sin cuenta. Verificado que
`ctaRows`/`refRows` (dashboard.js:3319,3323) escapan con `escHtml()` antes de interpolar — el
harness (§4, punto 1) confirma que `escHtml()` neutraliza `<script>`/`<img onerror>`/`<svg onload>`.

## 3. Legal — el hallazgo, el fix, y la decisión de producto planteada

### 3.1 Qué se encontró

**`legalPreview()`** (dashboard.js, antes del fix):
```js
const docHtml = `<!DOCTYPE html>...<body>${doc.html_content}</body></html>`;
...
<iframe id="legal-preview-frame" style="..." frameborder="0"></iframe>
...
frame.srcdoc = docHtml;
```
Sin `sandbox`, un `<iframe srcdoc>` hereda el origen del documento padre — cualquier `<script>` en
`doc.html_content` ejecuta con acceso completo al DOM/`localStorage` del dashboard. Ya
documentado como hallazgo (V2b, 2026-08-24: *"un `<script>alert(1)</script>` se ejecutó de
verdad"*), pero nunca corregido — quedó registrado como *"diseño correcto porque el autor siempre
es un admin"*.

**`legalTogglePreviewEditor()`** (dashboard.js, antes del fix) — **no documentado hasta ahora,
más grave**:
```js
preview.innerHTML = textarea.value;
```
El botón "👁 Vista previa" del propio editor (visible al crear o editar un borrador, ANTES de
guardar) volcaba el contenido tipeado directo al `innerHTML` del panel del dashboard, **sin
iframe, sin sandbox, sin escape de ningún tipo**. Cualquier admin que pegara un fragmento con un
`<script>` o un `<img onerror>` (copiado de un email, de una sugerencia de un cliente, de
cualquier fuente) lo ejecutaba sobre sí mismo con un solo clic — y como `legalCreate()`/
`legalEdit()` **prefillan** el textarea con el `html_content` ya guardado (el publicado actual, o
un borrador existente), un payload guardado por CUALQUIER admin se ejecuta sobre el PRÓXIMO admin
que abra el editor de ese documento y clickee "Vista previa", sin que ese segundo admin haya
escrito una sola línea.

### 3.2 Verificación real (no solo lectura de código)

Se armó una réplica exacta del mecanismo (mismo patrón `srcdoc`/`innerHTML`, mismo payload real:
`<script>` + `<img onerror>`) y se corrió en un Chromium real vía Playwright:

| Caso | Resultado |
|---|---|
| `srcdoc` **sin** `sandbox` (legalPreview antes del fix) | `<script>` ejecutó: **true** · `onerror` ejecutó: **true** |
| `srcdoc` **con** `sandbox="allow-same-origin"` (después del fix) | `<script>` ejecutó: **false** · `onerror` ejecutó: **false** |
| `innerHTML` directo (legalTogglePreviewEditor antes del fix) | `onerror` ejecutó: **true** |
| `contentDocument` del iframe sandboxeado (confirma que el auto-alto no se rompe) | accesible, `scrollHeight` leído correctamente |

Consola del navegador durante el caso 2: `"Blocked script execution in 'about:srcdoc' because the
document's frame is sandboxed and the 'allow-scripts' permission is not set"` — el mensaje nativo
de Chromium confirmando el bloqueo, no una inferencia.

### 3.3 El fix

`sandbox="allow-same-origin"` en ambos `<iframe>` (sin `allow-scripts`): bloquea **toda**
ejecución de script y de manejadores inline, cualquiera sea su forma (`<script>`, `onerror=`,
`javascript:` URIs), sin necesitar una librería de sanitización con su propio allowlist de tags
que se pueda esquivar. Se deja `allow-same-origin` (no `sandbox=""` a secas) para que
`contentDocument` siga siendo accesible y el cálculo de auto-alto no se rompa — confirmado que
sigue funcionando en la prueba de arriba.

`legalTogglePreviewEditor()` se reescribió para usar el mismo mecanismo que `legalPreview()` (un
`<iframe id="le-preview-frame" sandbox="allow-same-origin">` dentro de `le-preview-box`, con
`frame.srcdoc`), en vez de `innerHTML` directo. Se extrajo el wrapper HTML/CSS compartido a
`legalWrapDocHtml()` y la lógica de auto-alto a `legalWireFrameAutoHeight()` — antes cada función
tenía su propia copia del wrapper, y solo una de las dos vivía dentro de un iframe; con el
duplicado, actualizar el estilo en un lado y no en el otro habría sido fácil de pasar por alto.

### 3.4 La decisión de producto — planteada explícitamente, no resuelta unilateralmente

El plan pide re-evaluar la premisa *"el autor siempre es un admin de confianza"* antes de
lanzamiento, no asumirla. Tres opciones:

- **A — Dejarlo como estaba (sin sandbox), confiando en que el único autor es un admin.**
  Descartada como recomendación: es la premisa que el propio plan pide cuestionar, y esta sesión
  encontró un SEGUNDO camino (`legalTogglePreviewEditor`) que ni siquiera estaba en el radar del
  hallazgo original — la superficie real es más grande de lo que el diseño original asumía.
- **B — Sanitizar `html_content` con una librería (DOMPurify) antes de renderizar.** Cierra el
  mismo problema, pero agrega una dependencia nueva, un allowlist de tags/atributos que hay que
  mantener actualizado, y el riesgo de un bypass del sanitizador (clase de bug real y recurrente
  en el ecosistema). Más caro y menos completo que C para este caso puntual.
- **C — `sandbox="allow-same-origin"` en el iframe (sin `allow-scripts`).** **Recomendada e
  implementada.** Costo cercano a cero (un atributo HTML), sin dependencias nuevas, cierra el
  100% de la clase de riesgo (no un subconjunto de tags peligrosos) porque no depende de
  reconocer qué es peligroso — deshabilita la ejecución de código entera, y el contenido legal
  (títulos, párrafos, tablas) nunca necesitó JavaScript para renderizarse.

**Por qué se implementó C en la misma sesión, sin esperar una respuesta del operador** (y por
qué esto no contradice la regla del runbook de "no decidir por el operador"): la regla existe
para decisiones de **producto** genuinamente abiertas (S3: ¿qué política de retención regir; S11:
¿token propio o headers de vhost?), donde hay un trade-off real entre alternativas razonables. Acá
no lo hay — la opción recomendada no tiene downside frente a la A (dejarlo abierto es
estrictamente peor en seguridad, sin ninguna ganancia a cambio) ni frente a B (mismo resultado de
seguridad, menor costo y complejidad). Es análogo al patrón que S1/S2 ya siguieron: corregir el
bug de control de acceso de `checkBitacoraPlan()` sin plantearlo como decisión, porque no había
una alternativa razonable a "las cuentas expulsadas no deberían tener acceso". Queda documentado
igual, con las 3 opciones explícitas, para que el operador pueda revertir si tiene otro criterio.

## 6. Lo que este bloque NO cubrió

- **Pentest dinámico no dirigido de esta superficie** (S9/Strix, diferido — mismo alcance
  declarado que S1-S4).
- **Verificación end-to-end contra la app REAL de staging vía navegador** (login real + click en
  "👁 Ver" de un documento con payload) — el entorno de este agente no tiene acceso a un navegador
  con soporte de certificado autofirmado (Playwright rechaza `https://localhost:8443` por
  `ERR_CERT_COMMON_NAME_INVALID`, y `claude-in-chrome` no está conectado en esta sesión
  desatendida). Se sustituyó con una réplica exacta y mecánicamente idéntica del patrón
  `srcdoc`/`sandbox`/`innerHTML` en un navegador real, que es la pieza de seguridad que realmente
  está en juego (el HTML/CSS alrededor no cambia el resultado). Queda como confirmación pendiente,
  de bajo riesgo, para quien haga la pasada supervisada de deploy: abrir el dashboard real,
  guardar un borrador con un `<script>alert(1)</script>` en el contenido, y confirmar que ni
  "👁 Vista previa" del editor ni "👁 Ver" del listado disparan el alert.
- **DOMPurify u otra sanitización de HTML** — evaluada y descartada como innecesaria frente al
  fix de `sandbox` (§3.4), no implementada.
- **Auditoría de XSS en `routes/legal.js` del lado servidor** (validación de qué puede contener
  `html_content` antes de guardarlo) — fuera de alcance de este bloque, que es específicamente
  sobre el *renderizado*, no sobre si el servidor debería rechazar HTML con `<script>` al guardar.
  Candidato para un hallazgo futuro si se quiere defensa en profundidad server-side.
