## 2. Punto 2 — Headers del vhost `procuradortool.com`

**Verificado por SSH, solo lectura, el archivo real del servidor:**

```bash
ssh -i "C:/Users/JONATHAN/.ssh/do_procurador" root@142.93.64.94 \
  "cat /etc/nginx/sites-available/procuradortool"
```

Resultado — **el vhost completo, sin recortar**:

```nginx
# Landing page — procuradortool.com
server {
    listen 80;
    server_name procuradortool.com www.procuradortool.com;

    root /var/www/procurador/backend-server/public/landing;
    index index.html;

    access_log /var/log/nginx/landing-access.log;
    error_log  /var/log/nginx/landing-error.log;

    gzip on;
    gzip_types text/html text/css application/javascript;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**Confirma exactamente lo que el plan decía: cero `add_header`.** Y un dato adicional que el plan
no tenía: **el vhost solo escucha en el puerto 80 (HTTP puro), sin ningún bloque `ssl_certificate`**
(a diferencia de `procurador` —`api.procuradortool.com`— y `staging-procurador`, que sí tienen su
bloque 443 gestionado por certbot). El HTTPS público que ve el usuario en `procuradortool.com` lo
termina **Cloudflare** en el borde (confirmado por lo que ya documenta `CLAUDE.md`: *"SSL vía
Cloudflare"*), y Cloudflare hace proxy hacia este origen en HTTP plano. Esto no cambia el hallazgo
—headers de aplicación como CSP se agregan igual en el origen y Cloudflare los deja pasar— pero sí
importa para el bloque de config: no hay directiva `listen 443 ssl` donde insertar los headers, así
que el bloque nuevo va dentro del `server { listen 80; ... }` existente, no en un bloque separado.

**Bloque de config exacto que resolvería esto — documentado acá, NO aplicado al servidor:**

```nginx
# Agregar dentro de server { ... } en /etc/nginx/sites-available/procuradortool,
# después de gzip_types, antes de location /.
#
# Criterio: mismo espíritu que la CSP de Helmet en backend-server/server.js:54-71
# (B-5, 2026-06-01) — 'self' por defecto, 'unsafe-inline' donde el HTML real lo
# necesita (esta landing no usa nonces), sin scriptSrcAttr porque a diferencia
# del dashboard/portal, NINGÚN archivo de public/landing/ usa onclick="" inline
# (confirmado por grep, ver §4) — solo addEventListener.
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com data:; img-src 'self' data:; connect-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'self'; form-action 'self'" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

**Por qué estos valores exactos y no otros, verificado contra el árbol real de `public/landing/`
(4 archivos HTML: `index.html`, `terminos.html`, `privacidad.html`, `demo/index.html`) — no
copiado sin más de Helmet:**

- `script-src 'self' 'unsafe-inline'` **sin** `script-src-attr` — a diferencia de la CSP de Express
  (`server.js:60`, que sí necesita `scriptSrcAttr: 'unsafe-inline'` porque el dashboard/portal usan
  `onclick=""` inline), **los 4 archivos de la landing usan `addEventListener`, cero `onclick=""`**
  (`grep -c "onclick=" backend-server/public/landing/index.html` → `0`; mismo resultado en
  `demo/index.html`).
- `style-src ... https://fonts.googleapis.com` y `font-src ... https://fonts.gstatic.com` — los 4
  archivos cargan Google Fonts (`<link href="https://fonts.googleapis.com/css2?...">`); sin esto la
  CSP rompería la tipografía de toda la landing, no solo de `/demo/`.
- `connect-src 'self'` — no hay un solo `fetch()`/`XMLHttpRequest` en toda la landing (grep de
  `fetch(` y `XMLHttpRequest` en el árbol → 0 coincidencias); ni la demo ni el resto llaman a ningún
  API por JS, así que no hace falta abrir `connect-src` a `api.procuradortool.com`.
- `frame-ancestors 'self'` — no hay ningún `<iframe>` en el árbol (confirmado, §4), consistente con
  el `frameAncestors: ["'self'"]` de Express.
- `form-action 'self'` — no hay un solo `<form>` en el árbol (confirmado, §4); el registro es un
  `<a href="https://api.procuradortool.com/register/">`, un link, no un submit — así que no hace
  falta abrir `form-action` a `api.procuradortool.com`.

**No se agregó este header al servidor real** — es exactamente lo que la regla del bloque prohíbe.
Queda como bloque de config listo para copiar/pegar en la próxima pasada supervisada del operador.

## 3. Punto 3 — Ciclo de vida del token, corregido localmente

### 3.1 El fix

`backend-server/public/landing/demo/index.html`, función `haySesion()` (antes: línea 449-451, una
sola línea `return !!localStorage.getItem(TOKEN_KEY)`). Reemplazada por:

```js
// líneas 461-489 del archivo actual
function base64UrlDecode(str) {
  str = str.replace(/-/g, '+').replace(/_/g, '/');
  while (str.length % 4) str += '=';
  return atob(str);
}

function tokenVencido(token) {
  try {
    const partes = token.split('.');
    if (partes.length !== 3) return true; // no tiene forma de JWT → tratar como inválido
    const payload = JSON.parse(base64UrlDecode(partes[1]));
    if (!payload || typeof payload.exp !== 'number') return false; // sin exp, no se puede decidir
    return (Date.now() / 1000) >= payload.exp;
  } catch (_) {
    return true; // corrupto/no decodificable → fail-closed, tratarlo como vencido
  }
}

function haySesion() {
  try {
    const token = localStorage.getItem(TOKEN_KEY);
    if (!token) return false;
    if (tokenVencido(token)) {
      localStorage.removeItem(TOKEN_KEY);
      return false;
    }
    return true;
  } catch (_) { return false; }
}
```

**No verifica la firma del JWT** — no hace falta, y no tendría sentido: no hay clave pública en el
cliente ni la debería haber, y cualquier request real la sigue validando el backend igual. Solo lee
el claim `exp` para decidir si conviene seguir mostrando la sesión como activa **en este origen**, y
si venció, la borra. `haySesion()` se llama en cada `capituloBloqueado()`, que corre en cada render
de capítulo — así que el chequeo es continuo, no solo al cargar la página una vez.

Se agregó además la advertencia del punto 1 (§1), junto al comentario ya existente del gate de
sesión (líneas 418-434):

```js
// S11 (2026-09-01, revision-S11-2026-09-01.md): antes, haySesion() solo miraba si el
// token EXISTÍA — nunca si seguía vigente. El JWT del portal dura 8h (routes/auth.js,
// /auth/portal-login) y este origen NO lo borra nunca por sí solo (no hay logout acá,
// y el logout del portal tampoco lo alcanza — son orígenes distintos, ver el comentario
// de arriba). Sin este chequeo, un token robado o simplemente vencido seguía
// "desbloqueando" la demo indefinidamente.
```

### 3.2 Verificación puntual (real, no simulada)

`routes/auth.js:786` (`POST /auth/portal-login`) firma el token con `jwt.sign(..., { expiresIn:
'8h' })` (línea 821). Se corrió un script Node temporal (no commiteado) que:

1. Firma un JWT real con la misma librería `jsonwebtoken` que usa el backend, `expiresIn: '8h'`.
2. Firma otro con `expiresIn: -10` (vencido).
3. Corre la función `tokenVencido()` **extraída verbatim** del archivo real contra ambos, más un
   string sin forma de JWT y un JWT sintético sin claim `exp`.

```
OK   token de 8h recién emitido: NO vencido
OK   token con exp en el pasado: SÍ vencido
OK   string sin forma de JWT: SÍ vencido (fail-closed)
OK   JWT sin claim exp: NO vencido (no rompe el caso legítimo)
OK   jwt.sign con expiresIn SIEMPRE agrega exp numérico

5/5 PASS
```

El script se copió temporalmente a `backend-server/_tmp-verify-s11-token.js`, se corrió, y se borró
al terminar (no queda en el repo — confirmado con `git status` en §6). `node --check` sobre el
bloque `<script>` completo del archivo editado: **sintaxis limpia**.

### 3.3 Qué es esto y qué NO es

**Es la mitad de la Opción B** (§5) — la parte del código cliente. **NO incluye la otra mitad**

## 6. La decisión de producto — presentada, no tomada

Dos opciones, tal como las planteó el plan (§4 del plan, texto original conservado):

**Opción A — Token propio, efímero, sin privilegios.** El portal firma un valor opaco (no el JWT de
sesión) solo para desbloquear la demo, con vencimiento corto (minutos, no 8 horas) y **sin acceso a
ninguna API real** — ni `/usuarios/api/*` ni `/client/*` lo aceptarían como `Authorization`. Elimina
el bloque entero como clase de riesgo: aunque alguien lo robara, no abre nada. Requiere: un endpoint
nuevo (o una rama del existente) que emita ese token, y que `wireVerDemoLinks()` en
`usuarios/app.js:392-400` lo pida en vez de usar `getToken()` directo. Esfuerzo mayor que la Opción
B, pero cierra el bloque de forma definitiva, no mitigada.

**Opción B — Mínima, la implementada parcialmente en esta sesión.** Headers en el vhost (§2, no
aplicado) + que la demo descarte el token vencido (§3, aplicado localmente, no desplegado). Más
barata. **No cambia el mecanismo**: la demo sigue guardando el JWT de sesión completo, con acceso
real a la API, durante hasta 8 horas — solo reduce la ventana de exposición (headers mitigan XSS
futuro; expiración corta la ventana de un token robado de 8h a lo que quede de vigencia real en el
momento del robo, que en el peor caso sigue siendo 8h).

**Recomendación de este bloque, fundada:** para el volumen actual del producto (Beta, pocos
clientes, sin ningún hallazgo de XSS real hoy en la landing) **la Opción B alcanza** — es barata, ya
tiene la mitad hecha, y el riesgo real hoy es bajo (no hay vector de XSS activo). **Si la landing
alguna vez incorpora un script de terceros** (analytics, chat de ventas, un pixel de marketing — el
escenario que el propio plan señala como el más probable) **la recomendación cambia a Opción A sin
ambigüedad**: en ese momento la superficie de XSS deja de ser hipotética y el JWT completo de sesión
en ese origen se vuelve un riesgo activo, no residual. Queda como decisión del operador, no tomada
acá.
