## E4-1 (P-2) — XSS confirmado en el visor de Procuración/Informe individual

**Severidad:** 🟡 Medio · **Archivo:** `electron-app/visorModal_template.html` (474 líneas, completo)

El plan integral señalaba `visorModal_template.html` como candidato de XSS (`grep escapeHtml|sanitiz`
sin resultados). Esta revisión confirma el hallazgo con el detalle completo: **cero mitigación en
todo el archivo** (sin meta `Content-Security-Policy`, sin ninguna función de escape) y **5 puntos
concretos** donde texto libre extraído del PJN se interpola vía `innerHTML` sin sanear:

```js
// mostrarTabla() — línea 401-411
html += `<tr>
  <td class="mono">${expediente}</td>
  <td title="${caratula}" ...>${caratulaCorta}</td>        // ← carátula, dos veces (atributo + contenido)
  <td title="${dependencia}">${depCorta}</td>              // ← dependencia, dos veces
  <td>${situacion}</td>                                     // ← situación procesal
  ...`;

// abrirModal() — línea 436-441 (el más sensible: texto de una actuación judicial real)
exp.movimientos.forEach(mov => {
  bodyHTML += `<tr>
    <td>${mov.fecha}</td>
    <td><span class="tipo-badge">${mov.tipo}</span></td>
    <td>${mov.detalle}</td>                                 // ← el campo MÁS libre de todos
    ...`;
});
```

**Origen de los datos (verificado en el Bloque E1):** `caratula`, `dependencia`, `situacion`,
`mov.tipo` y `mov.detalle` vienen del scraping directo de la tabla de actuaciones del SCW
(`extraerTablaActuaciones` en `testM2.js`, backend-server) — texto que el sistema del PJN o el
letrado presentante determina, **sin ningún regex restrictivo** (a diferencia del número de
expediente, que sí está validado por formato en varios puntos del código).

**Impacto real, con un matiz importante que reduce la severidad frente a un XSS clásico:** el visor
se abre con `shell.openPath()` en el **navegador del sistema del usuario** (Chrome/Edge normal), no
dentro de una `BrowserWindow` de Electron con `contextBridge`. Esto significa que **el JS malicioso
que se ejecutara no tendría acceso a `window.electronAPI`** — la cadena hacia una posible ejecución
de archivo arbitrario que se documentó como riesgo condicionado en el Bloque E2 (hallazgo E2-3,
`open-file` sin validar) **no es viable por esta vía**, porque no hay ningún puente de contextBridge
en una pestaña de navegador abierta así. El impacto que sí queda vigente: phishing visual dentro del
propio informe (insertar contenido falso que aparente ser parte del expediente, para engañar al
abogado que lo lee), redirección a sitios maliciosos, o exfiltración de lo que sea visible en el DOM
del archivo local vía `fetch()`.

**Vector de explotación:** requeriría que alguien controle el contenido de un campo como el
"detalle" de una actuación en un expediente **real** del sistema SCW del PJN — un vector indirecto
(no es un input que el atacante controle directamente contra el producto), pero no descartable:
cualquier presentación en el PJN pasa por texto libre en varios de sus campos.

**Recomendación (no ejecutada, y de bajo costo dado el hallazgo E2-10 del Bloque E2):** el propio
proyecto ya tiene el patrón de escape correcto implementado y en producción — `generarVisorMonitoreo()`
en `electron-app/main.js` (el visor del Monitor de partes) usa:
```js
function esc(s) { return String(s||'').replace(/&/g,'&amp;').replace(/</g,'&lt;').replace(/>/g,'&gt;'); }
```
Portar esta misma función a `visorModal_template.html` y envolver los 5 campos señalados sería un
cambio acotado y de bajo riesgo — no hay que diseñar el mecanismo desde cero.

## E4-2 — Formula injection real en el Excel de Procuración

**Severidad:** 🟡 Medio · **Archivo:** `backend-server/scripts/procesarNovedadesCompleto.js:700-754`
(función `generarExcel`, hoja "Movimientos")

```js
resultados.expedientes.forEach(exp => {
    if (exp.movimientos && exp.movimientos.length > 0) {
        exp.movimientos.forEach(mov => {
            const row = sheetMovimientos.addRow({
                expediente: exp.expediente,
                fecha: mov.fecha,
                tipo: mov.tipo,          // ← texto libre del PJN, sin sanear
                detalle: mov.detalle,    // ← texto libre del PJN, sin sanear
                oficina: mov.oficina || '',   // ← texto libre del PJN, sin sanear
                caratula: exp.caratula,       // ← texto libre del PJN, sin sanear
                href: mov.viewHref || '',
                separador: '-'
            });
            ...
```

`ExcelJS` (`sheetMovimientos.addRow(...)`) escribe estos valores como celdas de tipo texto plano por
defecto, pero si el **contenido** de cualquiera de estos 4 campos comenzara con uno de los
caracteres que Excel/LibreOffice interpretan como inicio de fórmula (`=`, `+`, `-`, `@`), el
programa que abre el `.xlsx` lo evaluaría como fórmula al abrirlo, no como texto — el clásico
"CSV/Excel formula injection" (un patrón de vulnerabilidad bien documentado en la industria, con
vectores desde ejecución de comandos vía DDE hasta exfiltración de datos vía `HYPERLINK`/`WEBSERVICE`).

**Mitigantes reales que acotan la severidad:**
- Las versiones modernas de Excel muestran advertencias de seguridad explícitas antes de ejecutar
  fórmulas con enlaces externos o DDE — no es una ejecución silenciosa, requiere que el usuario
  ignore un aviso.
- El campo más probable de contener un `=` inicial real y legítimo (una fecha en formato `=DD/MM`
  mal tipeada, por ejemplo) es de baja probabilidad en el texto de una actuación judicial estándar.
- El vector de explotación requiere, igual que E4-1, que alguien controle el contenido de un campo
  de un expediente judicial real.

**Recomendación (no ejecutada):** anteponer un apóstrofe (`'`) o un espacio a cualquier valor de
celda que comience con `=`, `+`, `-`, `@`, antes de pasarlo a `addRow()` — mitigación estándar y de
bajo costo para este tipo de vulnerabilidad, aplicable en un solo helper reutilizado en los 4 campos.

## E4-3 — Mismo patrón en el visor de Informe por lote, riesgo acotado

**Severidad:** 🔵 Bajo · **Archivo:** `electron-app/informe/visor_informes_template.html:287-310`

```js
tr.innerHTML = `
  <td class="mono">${exp.expediente}</td>
  ...`;
```

Mismo patrón de `innerHTML` sin escape, pero acá **el único dato que se interpola es
`exp.expediente`**, que en este flujo (Informe por lote) siempre pasó por `parseExpedienteStr()`
(`main.js`), validado contra el regex `^(\w+)\s+(\d+)\/(\d{4})$` — no puede contener `<`, `>`, `&`
ni comillas. `exp.rutaPDF` (el otro dato interpolado, en un atributo `href`) se construye
internamente (`./${archivoEncontrado}`), no viene de datos externos. Documentado por completitud del
bloque, pero el riesgo real es prácticamente nulo con los datos que este flujo específico maneja.

## E4-4 — El tour de onboarding no está roto (verificación completa, contradice la sospecha del plan)

**Verificado sano.** El plan integral anticipaba como candidato de este bloque *"pasos del tour
rotos tras v2.7.33-43"* (los cambios de unificación de nombres de archivo, notificaciones, etc.).
Se verificaron los **18 selectores** que usan los 14 pasos de `tour.js` (algunos agrupados en
`targets: []` para spotlight múltiple) contra el `index.html` real:

`[data-action="procurar-hoy"]`, `#sidebarFechaLimite`, `[data-action="procurar-lote"]`,
`[data-action="informe"]`, `[data-action="monitor"]`, `#btnMainAction`, `.subtoolbar`,
`#browserToggleWrap`, `[data-action="visor"]`, `[data-action="excel"]`, `[data-action="descargas"]`,
`[data-action="limpiar-temp"]`, `[data-action="estadisticas"]`, `[data-action="configuracion"]`,
`[data-action="extension"]`, `#btnSidebarTour`, `#btnSidebarAsistente`, `#userChip`,
`#btnSidebarToggle` — **todos existen hoy**, confirmado por grep directo contra `index.html`.

Los cambios de v2.7.33-43 fueron a nivel de nombres de archivo de descarga y notificaciones de
Windows (backend/proceso principal), no tocaron los `data-action` del sidebar de la UI — por eso el
tour no se vio afectado. Adicionalmente, el mecanismo del tour ya es robusto por diseño: si un
selector no se encontrara, `showStep()` salta automáticamente al siguiente paso (línea 341:
`if (hasTarget && !firstRect) { nextStep(); return; }`) en vez de quedar trabado — una defensa
correcta contra futuros cambios de UI que si acaso rompan un selector puntual.

## E4-5 — `onboarding.js` reusa correctamente el mecanismo de credenciales cifradas

**Verificado sano.** `loadRememberedCredentials()`/`saveOrClearRemembered()` (líneas 229-274) usan
`safeStorageGet`/`safeStorageSet`/`safeStorageDelete` con las mismas claves literales fijas
(`'psc_accounts'`, `'psc_remember'`) ya revisadas en el Bloque E2 (hallazgo E2-1) — sin uso nuevo que
amplíe ese hallazgo. El cifrado real (`safeStorage.encryptString`, ligado a DPAPI/la cuenta de
Windows del usuario) ocurre en el proceso principal antes de tocar disco; la contraseña viaja en
claro solo por el canal IPC interno de Electron (renderer → main), que no es una superficie de
exposición externa.

## Lo verificado que está sano (no genera hallazgo adicional)

- **`generador_visor.js`/`generador_excel.js`** (Informe por lote, `electron-app/informe/`): ambos
  trabajan solo con `exp.expediente` (validado por regex), `exp.ok`, `exp.exitCode` — sin carátulas
  ni movimientos de texto libre. El `mensajeError` de `generador_excel.js` viene de `stderr` (logs
  de proceso), no de datos del PJN.
- **`onboarding.js` — flujo completo de los 4 pasos** (conexión, login, perfil Chrome, contraseña
  PJN): manejo de errores consistente, botones de reintento, y el email que se muestra en
  `showS2Success()` es el que el propio usuario tipeó en su propia sesión (sin vector de ataque real
  — sería auto-XSS sin beneficio para un atacante).
