## E1-1 — Tres scripts sin handler global de errores, con listeners de Puppeteer que hacen `throw`

**Severidad:** 🟠 Alto (razonamiento sólido sobre el comportamiento de Node.js + Puppeteer; no reproducido empíricamente porque requeriría forzar un 404/error SSL real contra el PJN).

**El patrón de riesgo.** `errorHandler.js` (usado por `testM2.configuracionesGenerales` en TODOS los flujos) instala listeners de eventos de Puppeteer que hacen `throw new Error(...)` **dentro del callback del evento**, no dentro de una cadena `await` que el código del script esté esperando:

```js
// errorHandler.js
page.on('requestfailed', (request) => {
    if (checkConnectionRefused && errorText.includes('ERR_CONNECTION_REFUSED')) {
        throw new Error('ERR_CONNECTION_REFUSED');   // ← dentro de un listener de evento
    }
    ...
});
page.on('response', (response) => {
    if (check404 && response.status() === 404) {
        throw new Error('HTTP_404');                  // ← ídem
    }
});
page.on('load', async () => {
    if (await verificarAdvertenciaSSL(page)) {
        throw new Error('SSL_BLOCK_SCREEN_DETECTED');  // ← callback async sin que nadie lo espere
    }
});
```

Este es un anti-patrón documentado en el ecosistema de Puppeteer: cuando el emisor del evento (Puppeteer, internamente, vía su conexión CDP) llama a estos listeners, un `throw` síncrono se propaga hacia arriba de la pila de llamadas **del emisor**, no del código del script — y para el listener `async`, un `throw` se convierte en una promesa rechazada que nadie tiene enganchada con `.catch()`. En ambos casos, si el proceso Node no tiene un handler global (`process.on('uncaughtException'/'unhandledRejection')`), Node **termina el proceso inmediatamente**, sin pasar por ningún `try/catch/finally` del código de usuario — porque el error nunca fue parte de la cadena de `await` que ese try/catch está vigilando.

**Verificado por grep: 3 scripts que llaman a `testM2.configuracionesGenerales()` (que instala estos listeners) no tienen ningún handler global:**

| Script | ¿Handler global? | Consecuencia si se dispara |
|---|---|---|
| `consultarscwpjn.js` | ❌ No | El `finally` que cierra el browser y borra `execution.lock` (líneas 503-512) **no se ejecuta** → Chrome huérfano + lock huérfano |
| `procesarMonitoreo.js` | ❌ No | Igual — el `cerrarNavegador(ctx.browser)` final (línea 327) no se alcanza |
| `procesarCustomExpedientes.js` | ❌ No | Igual — el `finally` (línea 367-369) no se alcanza |
| `informequickscwpjn.js` | ✅ Sí, pero ver **E1-2** | — |
| `listarSCWPJN.js` (vía `testM1`) | ✅ Sí (deliberadamente sin `exit`) | Recuperación correcta |
| `procesarNovedadesCompleto.js` | ✅ Sí (deliberadamente sin `exit`) | Recuperación correcta |

**Por qué importa:** un 404 real del PJN, un certificado SSL vencido, una redirección a una pantalla de error, o simplemente `ERR_CONNECTION_REFUSED` por un blip de red del usuario — cualquiera de estos, detectado por `errorHandler.js`, terminaría el proceso de Procuración individual, del Monitor, o de la Procuración de expedientes custom de forma abrupta, sin cerrar Chrome ni liberar el lock. Esto encaja con el patrón histórico de "Chrome huérfano" y "lock de ejecución huérfano" que el proyecto documentó haber sufrido en el pasado (ver CLAUDE.md, sesión 2026-07-24: *"lock de ejecución huérfano del 24/07, que license.js limpia solo en la próxima ejecución"*) — sin afirmar causalidad directa (no se pudo reproducir), pero es un mecanismo plausible y no descartado.

**Cómo verificarlo empíricamente (no hecho en esta pasada):** forzar un 404 real navegando a una URL rota del SCW mientras corre `consultarscwpjn.js`, y confirmar si el proceso Node muere sin el mensaje `"ERROR:" + error.message` esperado en stdout, y si Chrome queda vivo en el Task Manager tras el crash.

**Recomendación de fix (no ejecutada):** agregar a los 3 scripts el mismo patrón que ya usan `listarSCWPJN.js`/`procesarNovedadesCompleto.js` — `process.on('uncaughtException'/'unhandledRejection', ...)` que **solo loguea, sin `exit`**, dejando que el `try/catch/finally` normal del script actúe si el error vuelve a surgir por una vía capturable. Cambio mecánico y de bajo riesgo.

## E1-2 — `informequickscwpjn.js`: el handler global corta el sistema de reintentos que el mismo archivo implementa

**Severidad:** 🟡 Medio-Alto · **Archivo:** `backend-server/scripts/informequickscwpjn.js:87-94`

Este script SÍ tiene un handler global, pero hace `process.exit(1)` de inmediato:

```js
process.on('uncaughtException', function (err) {
    console.log('RESULT: {"error": "Error inesperado: ' + (err && err.message ? err.message : err) + '"}');
    process.exit(1);
});
```

El propio archivo implementa un sistema sofisticado de reintentos por sección (`estado_secciones.json`, backups incrementales por sección, `while (puedeReintentar(...))` con hasta 10 intentos configurables) y un manejo de errores estructurado (línea 903-930) que sí llama `cerrarNavegadorSeguro(browser)` correctamente. Pero el handler global de línea 87 **se salta todo eso**: si el error llega por la vía de un listener de evento (ver E1-1), el proceso termina en el acto, sin cerrar Chrome, sin agotar los reintentos configurados, y consumiendo un fallo "duro" por lo que podría haber sido un blip transitorio de red.

Esto contrasta directamente con los comentarios explícitos que dejaron en `listarSCWPJN.js`/`procesarNovedadesCompleto.js`:
```js
// NO llamar process.exit(1) — dejar que el sistema de reintentos maneje la recuperación.
```
— el mismo razonamiento debería aplicar acá, pero no se aplicó.

**Recomendación (no ejecutada):** que el handler global de `informequickscwpjn.js` llame `cerrarNavegadorSeguro(browser)` antes de salir (usando una referencia de módulo al browser activo, similar a `_activeBrowser` en `procesarCustomExpedientes.js`/`procesarMonitoreo.js`), o directamente adoptar el patrón "solo loguear, no exit" de sus archivos hermanos.

## E1-3 — El flujo "Procurar" puede listar expedientes incompletos sin ninguna señal de error

**Severidad:** 🟡 Medio-Alto · **Archivo:** `backend-server/scripts/testM1.js:714-716`, consumida por `procesarNovedadesCompleto.js:191`

`testM1.iterarListaExpedientes` — la función que el flujo "Procurar" usa para recorrer las páginas de expedientes de cada sección (LETRADO/PARTE/AUTORIZADO/FAVORITOS) — traga los errores por página:

```js
} catch (error) {
    console.error(`Error al procesar la página ${paginaActual}:`, error.message);
    // sin throw, sin break, sin marcar ningún flag de "incompleto" → el for sigue a la próxima página
}
```

Si una página intermedia falla (timeout esperando el número de página activo, DOM lento, un `waitForSelector` que expira), la función simplemente continúa al `paginaActual` siguiente **sin haber extraído los datos de la página fallida**, y retorna al final como si todo hubiera salido bien — `procesarNovedadesCompleto.js` recibe el array `expedientes` y no tiene forma de saber que faltan filas.

**Contraste directo:** la función análoga en `listarSCWPJN.js` (`iterarListaExpedientesConSimulacion`, línea 275-278) SÍ relanza:
```js
} catch (error) {
    console.error(`❌ Error en la página ${paginaActual}: ${error.message}\n${error.stack}`);
    throw error;   // ← activa el sistema de reintentos de nivel superior
}
```

**Por qué importa:** el "Procurar" (uno de los 3 flujos que el cliente paga) podría reportar "sin novedades" o "novedades parciales" para una sección que en realidad tenía más expedientes, sin ningún indicio en el resultado ni en los logs visibles al usuario — solo un `console.error` que nadie revisa en producción. Esto es exactamente la clase de bug que un plan de pruebas funcional (que verifica "¿el flujo terminó con éxito?") no detecta, porque el flujo SÍ termina con éxito — solo que con menos datos de los reales.

**Recomendación (no ejecutada):** hacer que `testM1.iterarListaExpedientes` relance el error (o al menos devuelva un flag `completo: false` como hace su análoga), y que `procesarNovedadesCompleto.js` trate ese caso con el mismo mecanismo de "RECUPERACIÓN AUTOMÁTICA" que ya usa para otros errores de sección (líneas 196-219).

## E1-4 — Un expediente bloqueado por SSL puede abortar todo el batch de Procuración individual

**Severidad:** 🟡 Medio · **Archivo:** `backend-server/scripts/consultarscwpjn.js:214-254`

El bloque "Verificar consistencia de la última página procesada" (que reutiliza el backup de una corrida anterior antes de decidir si reprocesar desde cero) llama `testM2.nuevaConsultaPublica(page, ...)` **sin ningún try/catch que lo envuelva** — a diferencia de los modos "soft" (línea 257) y "hard" (línea 320), que sí están protegidos:

```js
// líneas 214-254, SIN try/catch propio:
await testM2.nuevaConsultaPublica(page, exp.jurisdiccion, exp.numero, exp.anio);
...
if (htmlContent.includes("Pantalla de error SSL detectada en el contenido HTML")) {
    await cerrarNavegador(browser);           // ← cierra el browser
    throw new Error("SSL_BLOCK_SCREEN_DETECTED");  // ← sin catch aquí, sube al catch EXTERNO del script
}
```

Cuando esto ocurre, `browser` se cierra pero la variable `page` (del `for (const exp of expedientesInput)` en curso) queda apuntando a un objeto de un browser ya cerrado. Como el backup de expedientes (`backup_expedientes.json`) **persiste entre ejecuciones del script**, si un expediente *distinto*, más adelante en el mismo array `expedientesInput`, tiene backup de una corrida anterior, entrará en este mismo bloque sin protección — y `nuevaConsultaPublica(page, ...)` sobre una `page` de un browser cerrado lanzaría una excepción no capturada localmente, que se propaga hasta el `try/catch` externo de **todo el script** (línea 499-502), abortando **el resto del batch** en vez de degradar solo el expediente afectado con el mensaje "movimiento informativo" que el resto del flujo sí genera (línea 428-440).

**Recomendación (no ejecutada):** envolver el bloque de verificación de consistencia (214-254) en su propio `try/catch`, con el mismo criterio de degradación que el resto del script (marcar solo ese expediente como fallido y continuar con el siguiente).

## E1-5 — Log de monitoreo interno sin rotación, no aislado por usuario, con riesgo de crash silencioso

**Severidad:** 🟡 Medio · **Archivo:** `backend-server/scripts/monitoreo.js` (todo el archivo)

`setupMonitoring` (llamada siempre desde `testM2.configuracionesGenerales` con `{ logResponses: true, monitorDOM: true }`) escribe con `fs.appendFileSync` a `monitoring.log` en **cada** mensaje de consola del navegador, cada `pageerror`, cada request fallida, cada respuesta HTTP (incluyendo CSS/imágenes/JS de cada página del SCW), y cada evento `load`:

```js
const logFilePath = path.join(__dirname, 'monitoring.log');   // ← NO usa PROCURADOR_DATA_DIR
function log(message) {
    fs.appendFileSync(logFilePath, `[${new Date().toISOString()}] ${message}\n`);
}
page.on('response', (response) => { ...; log(...); });   // en cada respuesta HTTP de la sesión
```

Tres problemas:
1. **No respeta `PROCURADOR_DATA_DIR`** — el archivo vive en `__dirname`, compartido entre **todas las cuentas (CUIT)** que usan la app en la misma PC, violando el aislamiento por usuario que el fix D6 (2026-06-30) estableció explícitamente para las descargas.
2. **Nunca se rota ni se limpia** — no hay ningún código que trunque o borre `monitoring.log`. Con ejecuciones repetidas día tras día, el archivo crece indefinidamente.
3. **I/O síncrono de alta frecuencia dentro de listeners de eventos sin protección** — si `fs.appendFileSync` fallara (disco lleno, ruta no escribible en un build empaquetado con permisos distintos), el error ocurriría dentro de un callback de evento **sin try/catch**, con el mismo riesgo de crash no capturado descrito en E1-1.

**Recomendación (no ejecutada):** mover el log a `path.join(getDataPath(), 'logs', 'monitoring.log')` (aislado por usuario), agregar rotación por tamaño o fecha, y envolver el `fs.appendFileSync` en un try/catch silencioso.

## E1-6 — Asimetría de robustez entre el motor de Procuración/Informe/Monitor y el de Listado

**Severidad:** 🟡 Medio · **Archivos:** `testM2.js:257-409` (`iniciarSesion`) vs `testM1.js:241-478` (`iniciarSesion`)

`testM1.iniciarSesion` (usada solo por `listarSCWPJN.js` y la fase de listado de `procesarNovedadesCompleto.js`) envuelve toda la función en un `try/catch` que, ante cualquier error, restaura la ventana y **cierra el browser proactivamente si sigue conectado**, antes de relanzar:

```js
// testM1.js:461-477
} catch (error) {
    try { await showBrowser(page); } catch (_) {}
    try {
        if (browser && typeof browser.isConnected === 'function' && browser.isConnected()) {
            await browser.close();
        }
    } catch (closeError) { console.error(...); }
    throw error;
}
```

`testM2.iniciarSesion` (el motor que usan **Procuración, Informe y Monitor** — es decir, los 3 flujos que el plan de revisión identifica como "lo que el cliente paga") **no tiene ningún try/catch de este tipo** alrededor de la función completa — se limita a lanzar errores hacia arriba, confiando en que el llamador cierre el browser. Esto no es necesariamente un bug (varios llamadores sí lo hacen bien en su propio `catch`/`finally`), pero es una asimetría real: el motor más usado del producto tiene una capa de protección menos que su análogo de uso más acotado.

**Recomendación (no ejecutada):** espejar el patrón de cierre proactivo de `testM1.iniciarSesion` hacia `testM2.iniciarSesion`, como defensa en profundidad adicional a los fixes de E1-1/E1-2/E1-4.

## E1-7 — Archivos de control/estado no aislados por usuario (CUIT)

**Severidad:** 🔵 Bajo-Medio · **Consolidado de varios archivos**

El fix D6 (2026-06-30) aisló las **descargas** de cada usuario en `usuarios\<CUIT>\descargas\` vía `PROCURADOR_DATA_DIR`. Pero varios archivos de **control y estado** de los scripts siguen usando `path.join(__dirname, ...)`, quedando compartidos entre todas las cuentas de la misma PC:

| Archivo | Script | Propósito |
|---|---|---|
| `execution.lock` | `consultarscwpjn.js:76` | Detecta backups de una ejecución anterior |
| `pid_quickscw.txt`, `stop_quickscw.flag` | `informequickscwpjn.js:27,779` | PID del navegador / flag de detención manual |
| `monitoring.log` | `monitoreo.js:5` | Log de eventos de red (ver E1-5) |
| `<identificador>.txt`, `<identificador>_<tipo>.txt` | `testM1.js:805` (`guardarListaExpedientes`) | Listas de expedientes del flujo "Listado" |
| `execution.lock`, `backup_exp_*.json`, `estado_secciones.json`, `acumulador_resultados.json` | `listarSCWPJN.js:76,300,381,405,417` | Backups y estado del flujo "Listado" |

**Por qué importa (acotado):** si dos cuentas (CUIT) distintas ejecutan procesos en la misma PC de forma solapada — escenario posible pero no el uso típico documentado del producto (una PC por profesional) — estos archivos compartidos podrían pisarse entre sí: un `execution.lock` de una cuenta podría hacer que el chequeo de "backup de ejecución anterior" de otra cuenta se comporte de forma inesperada, o un `stop_quickscw.flag` de una cuenta podría (en teoría) afectar la ejecución de otra si los procesos corrieran en paralelo. El candado real de concurrencia por usuario vive server-side (`active_executions`/`license.js`), así que el impacto práctico depende de si ese candado ya previene el solapamiento entre CUITs en la misma máquina (no verificado en esta pasada — pertenece al Bloque E2/E3).

**Recomendación (no ejecutada):** mover estos archivos a `path.join(getDataPath(), ...)` (mismo patrón que ya usan las descargas), consistente con D6.

## E1-12 — Variable de modo hardcodeada anula una rama de código

**Severidad:** 🔵 Bajo · **Archivo:** `backend-server/scripts/consultarscwpjn.js:448-467`

```js
const modoSeleccionado = 'quick5mam'; // modo usado en iterarTablaActuaciones
if (mov.archivo && mov.archivo !== "nn" && modoSeleccionado === 'quick5') {
```
`modoSeleccionado` se fija a `'quick5mam'` dos líneas antes de compararlo contra `'quick5'` — la condición nunca es verdadera. Sin impacto real porque el modo efectivamente usado (`quick5mam`) tiene `maxDownloadsPerPage: 0`, así que `mov.archivo` nunca sería distinto de `"nn"` de todas formas.
