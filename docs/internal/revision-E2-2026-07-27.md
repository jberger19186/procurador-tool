## E2-1 — Path traversal en `safe-storage-set/get/delete`

**Severidad:** 🟡 Medio (defensa en profundidad ausente; no hay explotación conocida con el código actual) · **Archivo:** `electron-app/main.js:766-802`

Los 3 handlers reciben `key` directo del renderer sin ninguna sanitización, y lo usan para construir una ruta de archivo:

```js
ipcMain.handle('safe-storage-set', (_, key, value) => {
    ...
    fs.writeFileSync(path.join(userData, `${key}.enc`), encrypted);
});
ipcMain.handle('safe-storage-delete', (_, key) => {
    const filePath = path.join(userData, `${key}.enc`);
    if (fs.existsSync(filePath)) fs.unlinkSync(filePath);   // ← borra sin validar
});
```

`path.join()` no previene traversal: un `key` como `"../../../../Users/usuario/Documents/algo"` resolvería fuera de `userData`. El handler `safe-storage-delete` es el más sensible — permitiría borrar cualquier archivo dentro de los permisos del proceso.

**Verificado por grep: los 7 call sites reales (2 en `login.js`, 4 en `onboarding.js`, contando ambos preloads) usan siempre literales fijos** (`'psc_accounts'`, `'psc_remember'`) — el `key` nunca proviene de datos de usuario ni de datos externos en la práctica actual. El vector de explotación requeriría comprometer el propio código fuente de `login.js`/`onboarding.js` (que no cargan contenido remoto ni ejecutan HTML de terceros), no un ataque remoto vía datos del PJN.

**Recomendación (no ejecutada):** agregar `path.basename(key)` o una whitelist antes de construir `filePath`, como defensa en profundidad — barato y sin riesgo de romper el uso actual.

## E2-2 — Verificación de integridad de scripts: fail-open ante errores no clasificados

**Severidad:** 🟡 Medio · **Archivo:** `electron-app/src/auth/authManager.js` (3 sitios)

El proyecto implementa 3 etapas de verificación de integridad sobre los scripts descargados (firma RSA + checksum), pero las 3 comparten el mismo patrón: solo bloquean ante las dos excepciones específicas (`SignatureVerificationError`, `ChecksumMismatchError`); **cualquier otra excepción del verificador se loguea con `console.warn` y el flujo continúa como si la verificación hubiera pasado**.

```js
// loadScript() — verificación al descargar (línea 215-259)
} catch (verifyError) {
    if (verifyError instanceof SignatureVerificationError) { return {success:false, ...}; }
    if (verifyError instanceof ChecksumMismatchError) { return {success:false, ...}; }
    // Error genérico de verificación - log pero no bloquear
    console.warn(`⚠️ Error verificando ${scriptName}:`, verifyError.message);
}
// ... el script se guarda en caché igual, unas líneas más abajo, sin ningún guard.

// executeRemoteScriptAsLocal() — checksum etapa 2 (línea 571-585) y etapa 3 (línea 618-635):
// mismo patrón exacto en ambas.
```

**Por qué importa:** esto es un diseño de "fail-open" consistente en las 3 capas de defensa que el proyecto construyó específicamente para garantizar que solo código firmado y verificado se ejecute. Si el verificador (`src/security/scriptVerifier.js`, zona protegida) lanzara una excepción no anticipada por una razón distinta a una firma/checksum inválidos — un error de parsing, un timeout, un bug del propio verificador — el script se ejecutaría de todas formas sin haber sido verificado. Esto podría ser una decisión consciente (priorizar disponibilidad ante fallos transitorios del verificador sobre bloquear al usuario), pero no está documentada como tal en el código, y las 3 repeticiones idénticas sugieren que es más un patrón heredado que una decisión explícita revisada.

**Nota de alcance:** el cambio, si se decide hacer, tocaría la interacción entre `authManager.js` (en alcance de E2) y `src/security/scriptVerifier.js` (zona protegida, `⛔ NO TOCAR` según CLAUDE.md) — **no se propone ni se ejecuta ningún fix acá**; queda documentado para que el operador decida si el fail-open es intencional o merece revisarse, dado que tocar el comportamiento requeriría entender primero por qué el verificador podría lanzar una excepción "genérica" en la práctica.

## E2-3 — `open-file` no valida su entrada (riesgo condicionado a P-2 del plan integral)

**Severidad:** 🔵 Bajo-Medio (condicionado) · **Archivo:** `electron-app/main.js:1534-1547`

```js
ipcMain.handle('open-file', async (event, filePath) => {
    if (!fs.existsSync(filePath)) return { success: false, error: 'Archivo no encontrado' };
    await shell.openPath(filePath);   // ← abre CUALQUIER ruta que reciba, sin validar
});
```

El handler confía ciegamente en el `filePath` que le pasa el renderer. `shell.openPath()` abre el archivo con la aplicación asociada del sistema — si el archivo fuera un `.exe`/`.bat`/`.cmd`, esto ejecutaría código.

**Verificado por grep: los 4 call sites reales en `renderer.js`** (líneas 1212, 1238, 1459, 1504) pasan siempre `result.path` o `rutaHTML` — rutas que el propio `main.js` construyó (`get-visor-path`, `get-latest-excel`, el resultado de un proceso), nunca datos crudos extraídos de un expediente del PJN.

**Por qué igual merece documentarse:** el plan integral (`plan-revision-integral-2026-07-27.md`, hallazgo P-2) ya señaló que los visores HTML embeben datos del PJN sin escapar (`innerHTML` sin sanitizar). Si ese hallazgo se confirmara como explotable — un atacante lograra inyectar HTML/JS en un campo de un expediente judicial real que termine en el visor — y ese JS inyectado llamara a `window.electronAPI.openFile(...)` con una ruta arbitraria, la falta de validación en este handler completaría la cadena hacia una posible ejecución de archivo arbitrario en la máquina del usuario. **Es una cadena de dos eslabones, ninguno confirmado como explotable individualmente hoy**, pero vale la pena que quien revise P-2 tenga presente que `open-file` no aporta ninguna defensa adicional si esa cadena se completara.

**Recomendación (no ejecutada):** validar que `filePath` resuelva dentro de directorios esperados (la carpeta de descargas del usuario, o `getDataPath()`), o al menos rechazar extensiones ejecutables (`.exe`, `.bat`, `.cmd`, `.scr`, `.ps1`).

## E2-4 — `ScriptExecutor` + `AuthManager.executeScript()`: ~280 líneas de código muerto

**Severidad:** 🔵 Bajo · **Archivos:** `electron-app/src/scripts/scriptExecutor.js` (186 líneas, completo) + `electron-app/src/auth/authManager.js:283-378` (el método `executeScript`)

`ScriptExecutor` implementa un sandbox `vm.createContext` completo, con un `require()` personalizado que busca módulos en la caché de scripts. `AuthManager` lo instancia en su constructor (`this.scriptExecutor = new ScriptExecutor(...)`) y expone un método `executeScript(scriptName, params)` que lo usa.

**Verificado por grep: `authManager.executeScript(` no tiene ningún consumidor** en todo el codebase — ningún handler de `main.js` lo llama. Todos los flujos reales de ejecución (Procuración, Informe, Monitor, Custom) usan `authManager.executeRemoteScriptAsLocal(...)`, que hace `fork()` de un proceso hijo real — el único camino viable para scripts que usan Puppeteer (`puppeteer.launch()` no puede correr dentro de un `vm.createContext` sandbox de forma funcional).

Esto es una implementación completa y vestigial de una arquitectura de ejecución anterior. No es un riesgo de seguridad activo (nadie la invoca), pero es superficie de mantenimiento innecesaria y una fuente de confusión real: un futuro desarrollador podría asumir que este es el camino de ejecución "sandboxeado y seguro" y el otro (`executeRemoteScriptAsLocal`, fork con scripts cifrados en disco) el alternativo, cuando es al revés — el fork es el único que se usa.

**Recomendación (no ejecutada):** eliminar `ScriptExecutor`, el método `executeScript()` de `AuthManager`, y la instanciación en el constructor — mismo criterio que ya se aplicó en RI-4 (2026-07-22) para la distribución CRX/ZIP.

## E2-5 — `generate-extension-pdf`: otro vestigio de la distribución CRX/ZIP que RI-4 no completó

**Severidad:** 🔵 Bajo · **Archivo:** `electron-app/main.js:629-723` (el handler completo, ~95 líneas)

Genera un PDF con instrucciones para instalar la extensión manualmente vía "Cargar extensión sin empaquetar" en `chrome://extensions`, con un texto que dice *"La extensión 'PJN – Automatización' aparecerá en la lista"* y una nota sobre "si descargás una nueva versión, deberás repetir este proceso" — instrucciones para el flujo de distribución CRX/ZIP que RI-4 (2026-07-22) documentó haber eliminado (`downloadExtension()`, `install-extension`, `check-extension-version`, ver el propio comentario en `main.js:496-502`).

**Verificado por grep: `generateExtensionPdf` se expone en ambos preloads (`preload.js:149`, `preload-onboarding.js:15`) pero no tiene ningún consumidor** — ni en `.js` ni en `.html` de todo `electron-app`. La extensión hoy se instala desde la Chrome Web Store (un solo clic), no requiere "cargar sin empaquetar" ni generar un PDF con la ruta de una carpeta.

**Recomendación (no ejecutada):** eliminar el handler completo + el bridge en ambos preloads, mismo criterio que el resto de la limpieza RI-4.

## E2-6 — Lectura de estadísticas busca una carpeta eliminada en v2.7.33

**Severidad:** 🔵 Bajo · **Archivo:** `electron-app/src/auth/authManager.js:811-834`

Tras cada ejecución exitosa (`child.on('close', ...)`), el código intenta leer estadísticas desde:
```js
const procesosPath = path.join(tempDir, 'descargas', 'procesos_automaticos');
if (fs.existsSync(procesosPath)) { ... }
```
La subcarpeta `procesos_automaticos/` fue eliminada en la unificación de nombres de v2.7.33 (documentado en CLAUDE.md, sesión 2026-06-30: *"La subcarpeta procesos_automaticos/ desaparece (archivos directamente en descargas/)"*) — los scripts actuales escriben sus resultados directo en `descargas/`, sin esa subcarpeta intermedia. Esto significa que `fs.existsSync(procesosPath)` siempre es `false` desde esa versión, y el bloque cae siempre al `catch` (línea 835-838), notificando "sin detalles". No rompe nada (tiene fallback silencioso), pero es trabajo de `fs.readdirSync` que nunca encuentra lo que busca, y confunde a quien lea el código pensando que esa ruta sigue siendo válida.

**Recomendación (no ejecutada):** actualizar la ruta a `path.join(tempDir, 'descargas')` directamente, o eliminar el bloque si las estadísticas ya no son necesarias (dado que `updateRunStats()` en `main.js` ya lleva estadísticas propias).

## E2-7 — `runProcessLogic` sin optional chaining en `mainWindow.webContents.send` (sin escenario de riesgo confirmado)

**Severidad:** ℹ️ Informativo · **Archivo:** `electron-app/main.js:1196-1233`

`runProcessLogic` es invocada tanto por el handler `run-process` (disparado desde un clic real, con `mainWindow` siempre viva) como por `dailyVerification.js` (que su propio comentario describe como corriendo *"sin pasar por un evento de renderer"*). Dentro de la función, varios `mainWindow.webContents.send(...)` no usan optional chaining (`mainWindow?.webContents.send(...)`), a diferencia de otros puntos del archivo que sí lo hacen (ej. los handlers de `autoUpdater`, línea 55-73).

**Verificado:** revisando los 3 disparadores reales de la verificación diaria (`checkAndMaybeRun()` tras login — con `mainWindow` ya creada 5s antes; `startHorarioWatcher()` cada 10 min — solo corre mientras la app está viva, y en Windows cerrar `mainWindow` mata la app entera; `runNow()` manual desde DevTools — requiere la ventana abierta), **no se encontró un camino de ejecución realista donde `mainWindow` sea `null` en este punto hoy**. Si tal excepción ocurriera, `dailyVerification.runVerification()` la capturaría en su propio `try/catch` (línea 160-166 de `dailyVerification.js`) sin romper el módulo — pero el `catch` de `runProcessLogic` (línea 1231-1233) haría el mismo `mainWindow.webContents.send(...)` sin protección, lo cual sí se propagaría sin capturar hacia el llamador.

**Recomendación (no ejecutada, bajo costo si se quiere aplicar igual):** agregar optional chaining a los 6 `mainWindow.webContents.send(...)` de `runProcessLogic` como defensa en profundidad, aunque no se haya encontrado un escenario de disparo real.

## Lo verificado que está sano (no genera hallazgo)

- **`preload.js`**: `contextBridge.exposeInMainWorld` + `ipcRenderer.invoke` en los 3 archivos de preload (`preload.js`, `preload-onboarding.js`) — sin `nodeIntegration`, con `contextIsolation:true` en las ventanas que importan (login, main, onboarding). No se expone ningún módulo de Node directamente al renderer.
- **`isSafeHttpUrl()` (`main.js:577-585`)**: protección explícita y bien razonada contra flag injection (`url.startsWith('-')`) y esquemas peligrosos — solo permite `http:`/`https:`. Usada consistentemente en `open-url-in-chrome` y `open-external-url`. Documentado como fix consciente (B6).
- **`getUserDataDir(cuit)` (`main.js:971-975`)**: sanitiza el CUIT con `replace(/\D/g, '')` antes de usarlo en una ruta — previene path traversal vía CUIT malicioso.
- **`_lastKnownCuit` + su limpieza en `logout` (`main.js:910`)**: el comentario M5 documenta explícitamente por qué se limpia al cerrar sesión (evitar que un usuario B herede el cache de CUIT de un usuario A tras un blip de red) — fix ya aplicado y consistente.
- **`checkSubsystemLimit()` (`main.js:1098-1143`)**: bien documentado, con el razonamiento histórico completo (por qué se removió el gate por `payment_provider`) y el soporte para lotes parciales (C2) correctamente implementado.
- **`backendClient.js`**: `rejectUnauthorized: true` en el agente HTTPS (sin bypass de TLS); interceptor de token limpio; todos los métodos siguen el mismo patrón de manejo de error. El método genérico `.request()` solo se usa con endpoints literales fijos (verificado por grep en los 14 call sites de `monitor-*`).
- **`dailyVerification.js`**: contención de lock bien pensada (si lo único que falló fue "ya hay un proceso en ejecución", no cuenta como fallo del día), guarda el resultado local antes de reportar al backend (no se pierde si el POST falla), y cada llamada a `runProcessLogic`/`runInformeLogic` está en su propio try/catch.
- **`run-process-custom` (C2, `main.js:1342-1441`)**: el pre-chequeo de `checkSubsystemLimit('batch', ...)` y el cap de `expedientesPerRun` en el proceso principal (no solo en el renderer) están correctamente aplicados — confirma que el fix C2 de julio sigue vigente.
