# Verify V2a — Dashboard admin: Usuarios, Tickets, Planes (2026-08-24)

> Bloque V2a de `docs/internal/plan-verificacion-runtime-2026-08-23.md`.
> Ejecutado con Sonnet 5, esfuerzo alto (según el propio plan).

**Verdict:** PASS con 1 hallazgo nuevo (bug de UX menor, no corregido) y la confirmación empírica
extensa de un patrón ya señalado en V1b.

**Claim:** Usuarios (ficha completa, ajustes manuales, usos extra, beneficios, cambio de plan,
activar/suspender, editar email), Tickets (hilo, respuesta interna vs externa, prioridad IA, editar

nativos que este bloque dispara (ver hallazgo confirmado abajo). **⚠️ Contra stub, no contra el
dashboard real de producción**, tal como exige el plan — ninguna acción tocó datos reales.

## Findings

- ⚠️ **Hallazgo #1 (bug de UX, no corregido): el éxito de crear un usuario dispara un `alert()`
  nativo, no un mensaje inline como el resto del dashboard.** `submitAddUser()`
  (`dashboard.js:449` aprox.) hace `alert(r.message || 'Usuario creado.')` tras el `POST
  /admin/users` exitoso. Confirmado con Playwright: `["alert" dialog with message "Usuario
  nuevo.usuario.v2a@test.local creado correctamente."]`. No es un bug de datos — el usuario se
  crea bien — pero es inconsistente con el resto del flujo (que usa `showAlert()` inline, ej. en
  `saveRegistroData`, `adminSuspendUser`) y **traba cualquier automatización o QA** que no maneje
  el diálogo explícitamente, exactamente como U9.3 documentó para el checkout del portal. Fix
  sugerido: reemplazar por `showAlert(document.getElementById('...'), r.message, 'success')` +
  cerrar el modal, mismo patrón que el resto de las acciones de esta misma sección.
- 🔍 **Confirmación empírica extensa de un patrón ya señalado en `verify-V1b-2026-08-24.md`
  (hallazgo #2): el dashboard admin depende masivamente de `confirm()` nativo.** Esta corrida
  disparó y manejó **9 diálogos nativos distintos** (cambio de plan, reactivar, editar email,
  activar cuenta, vencimiento de plan ×2, desactivar/activar plan ×2, más el `alert()` del
  hallazgo #1) — todos en Usuarios y Planes. El único flujo destructivo/con-efecto que usa un
  modal **custom** (no nativo) es `adminSuspendUser`. Por lectura de código hay más instancias sin
  ejercitar en esta corrida: `rejectUserBlock` usa además un `prompt()` nativo (motivo de
  rechazo). Ninguno de los 9 probados falló — todos funcionan correctamente — pero cualquier
  automatización contra este dashboard necesita manejar diálogos nativos en casi cada acción con
  efecto, no es un caso aislado.
- 🔍 El escape de HTML se confirmó en 2 lugares nuevos del dashboard (nombre de usuario, mensaje de
  ticket) con payloads reales (`<img onerror>`, `<script>`) — correcto en ambos, consistente con
  el fix histórico de XSS-1.
- 🔍 La ficha de usuario, el hilo de tickets y el form de planes son grandes (varias decenas de
  campos/acciones entre los 3) pero no se encontró ningún camino roto — el volumen del bloque
  (razón del esfuerzo "alto" del plan) se confirmó real: cubrirlo tomó sustancialmente más pasos
  que V1a o V1b, sin que eso por sí solo indicara fragilidad.

### No cubierto en este bloque (documentado, no es un hallazgo)

- `rejectUserBlock`/`rejectUserKeepTrial` (rechazar/bloquear un registro pendiente, con
  `prompt()` nativo para el motivo) no se ejercitó — mismo patrón de diálogo nativo ya
  ampliamente confirmado en otras 9 instancias de este bloque, riesgo marginal de encontrar algo
  distinto.
- `sendPasswordReset` (blanquear contraseña) y `assignCuit` no se probaron — acciones de una sola
  línea, bajo riesgo.
- Los usuarios "pendientes" (`renderPendingUsers`, con `activateUser`/`rejectUserBlock` desde una
  vista separada) no se recorrieron — es la misma lógica que ya se probó desde la ficha de
  usuario (`saveRegistroData` con transición a `active`), vista distinta, mismo backend.
- Pagos, Facturación, Feriados, Monitor, Legal, Métricas, Diagnóstico, Scripts — eso es V2b, fuera
  del alcance de este bloque.
