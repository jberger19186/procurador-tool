### 2.2 🚨 El circuito de baja real — 2 bugs de código en el cron 5e, corregidos

**Cómo se encontró:** siguiendo la instrucción del plan de leer el código real, no asumir el
contrato — `server.js:760` (`// 5e. Liberación de CUIT a 90 días post-cancelación`) antes del fix:

```js
const result = await pool.query(`
    UPDATE users SET cuit = NULL, updated_at = NOW()
    WHERE registration_status = 'cancelled'
      AND updated_at < NOW() - INTERVAL '90 days'
      AND cuit IS NOT NULL
    RETURNING id
`);
```

**Bug 1 — la condición mide el campo equivocado.** `users` tiene un trigger
(`update_users_updated_at`, `BEFORE UPDATE ... FOR EACH ROW`, `NEW.updated_at = NOW()`, **sin
condición de columna**) que pisa `updated_at` en **cualquier** UPDATE de la fila. `/auth/portal-login`
(`routes/auth.js:816`) hace `UPDATE users SET last_login = NOW() WHERE id = $1` en cada login
exitoso — y ese endpoint **permite loguearse a cuentas `cancelled`** a propósito (`hardBlocked` en
`routes/auth.js:786-814` solo bloquea `rejected`; `cancelled` puede entrar a ver facturas o
re-suscribirse). Consecuencia verificada: **una cuenta cancelada que entra al portal una sola vez
dentro de la ventana de 90 días reinicia el contador indefinidamente** — el mecanismo nunca
dispararía para la cuenta que el propio sistema diseñó para que vuelva a entrar (re-suscripción).

**Bug 2 — columna muerta.** `users.cuit_deleted_at` existe desde la migración
`database/migrations/005_fase5_payments.sql:30-32` (`COMMENT ON COLUMN users.cuit_deleted_at IS
'CUIT anulado 90 días post-cancelación (retención legal)'`), pero **ningún código de todo el repo la
escribía nunca** (grep completo, 0 coincidencias fuera de la migración y `schema.sql`) — el cron
original solo tocaba `cuit`, nunca `cuit_deleted_at`. Confirmado por SQL antes del fix: **0 filas**
con `cuit_deleted_at IS NOT NULL` en toda la historia de producción, y era estructuralmente imposible
que hubiera alguna.

**Fix aplicado** (`server.js:760-799`): la condición se mueve a `user_events.event_type =
'subscription_cancelled_expired'` (el evento que `server.js:829`, cron 5f, inserta **una sola vez**,
en el momento exacto de la transición real a `cancelled` — es el único lugar de todo el repo que
setea ese `registration_status`, confirmado por grep) con `MAX(created_at)` para cubrir correctamente
un ciclo cancelar→reactivar→cancelar, y se agrega `cuit_deleted_at = NOW()` al UPDATE:

```sql
UPDATE users u SET cuit = NULL, cuit_deleted_at = NOW(), updated_at = NOW()
WHERE u.registration_status = 'cancelled'
  AND u.cuit IS NOT NULL
  AND (
    SELECT MAX(ev.created_at) FROM user_events ev
    WHERE ev.user_id = u.id
      AND ev.event_type = 'subscription_cancelled_expired'
  ) < NOW() - INTERVAL '90 days'
RETURNING id
```

**Verificado con 4 fixtures y 14 aserciones, todas PASS** (harness
`dev-tools/verify-s3-retencion-cuit.js`, contra staging): cancelado hace 100 días sin login posterior
→ se libera (no-regresión) · cancelado hace 100 días **con un login simulado** (`UPDATE users SET
last_login=NOW()`, replicando exactamente lo que hace `/auth/portal-login`) → **se libera igual**
(el fix, antes NO se habría liberado) · cancelado hace solo 10 días → no se toca · re-cancelado hace
5 días con un evento viejo de 200 días → **no se libera** (confirma que se usa el evento MÁS
RECIENTE, no cualquiera) · `cuit_deleted_at` queda seteado en los 2 casos liberados y sigue `NULL` en
los no liberados · segunda corrida de la misma query → 0 filas nuevas (idempotente).

**Desplegado exclusivamente a staging** (backup previo con `ops/backup-now.sh staging`, `pm2 restart
procurador-staging`, `/health` 200 antes y después). **Producción sigue con el código anterior** —
el deploy ahí es la pasada supervisada aparte que exige el runbook (regla §3.1).

### 2.3 ⭐ La brecha real: no hay ningún camino que borre PII completa — decisión del operador

Con el fix de 2.2, el mecanismo automatizado **funciona como fue diseñado** — pero lo que hace,
diseñado correctamente, es limitado: **solo anula el CUIT.** Confirmado por lectura completa del
esquema de `users` (`\d users` en producción) y por grep de `DELETE FROM users` en todo el repo
(0 endpoints — los únicos usos de ese patrón están en `dev-tools/`, scripts de mantenimiento manual
que un admin corre a mano, nunca en `routes/`):

| Campo de PII en `users` | ¿Se borra/anonimiza en algún momento del ciclo de vida? |
|---|---|
| `cuit` | Sí — a los 90 días de `cancelled` (recién corregido) |
| `nombre`, `apellido` | **Nunca** |
| `domicilio` (jsonb: calle, número, localidad, provincia) | **Nunca** |
| `telefono` | **Nunca** |
| `email` | **Nunca** |

Y todo lo relacional que cuelga de `user_id` (pagos, facturas, tickets, entradas de Bitácora,
eventos) sigue existiendo para siempre, porque **la fila de `users` nunca se borra** — solo se le
anula un campo. La Política de Privacidad (`public/privacidad/index.html:308`) promete
*"Supresión ('derecho al olvido'): solicitar la eliminación de sus datos, salvo que exista obligación
legal de conservarlos"* y responder en *"un plazo máximo de 5 días hábiles"* (línea 310) — hoy,
cumplir esa promesa exige que un admin escriba SQL a mano (el mismo patrón que ya se usó para borrar
los 6 fixtures de QA el 28/08), sin ningún script versionado ni probado para el caso real de un
cliente pidiéndolo.

**3 opciones, sin decidir (regla del runbook — este bloque no elige por el operador):**

- **A — Endpoint admin de borrado completo.** Un botón en la ficha del usuario que anonimiza
  nombre/apellido/domicilio/telefono y neutraliza el email (hash o vacío), dejando el resto de las
  tablas relacionadas intactas pero desvinculadas de la identidad real. Requiere decidir qué hacer
  con `invoices` (ver 2.4) y con el propio `id` (¿se conserva como referencia huérfana o se elimina
  la fila entera con CASCADE?). Es la solución estructural, mayor costo de implementación.
- **B — Extender el cron 5e ya corregido.** Un paso adicional (mismo disparador de 90 días, o uno
  propio) que, después de anular el CUIT, anonimice también nombre/apellido/domicilio/teléfono.
  Menor costo que A (mismo mecanismo, más columnas), pero sigue sin dar respuesta **inmediata** a una
  solicitud puntual — solo automatiza lo que hoy sería manual, con el mismo plazo de 90 días.
- **C — Formalizar el proceso manual actual.** Escribir y versionar un script de referencia (mismo
  patrón que `reset-test-data.sql`/`_delete_user_by_email.sql`, que ya existen como herramientas de
  desarrollo pero no están pensados ni probados como procedimiento de atención a una solicitud real)
  con el que un admin pueda responder una solicitud de supresión real dentro del plazo prometido, sin
  improvisar SQL cada vez. Es el mínimo viable inmediato: no requiere tocar código de producto, cierra
  la brecha entre "lo prometido" y "lo que existe" para operar hoy con 0 clientes reales y 0 bajas
  jamás ejercidas.

**Recomendación no vinculante:** C ahora (bajo costo, cierra la brecha operativa inmediata); A o B
antes del lanzamiento masivo, cuando el volumen de bajas reales lo justifique.

## 3. S4 — Abuso del registro público y farmeo del trial

> Todo contra **staging**, con tráfico HTTP real (no simulado). `allow_public_register=true` en
> staging, igual que en producción hoy.

### 3.1 CUIT único — freno de unicidad, no de identidad (confirmado con 200 CUITs reales)

`validarCuit()` (`routes/auth.js:14-25`) implementa el algoritmo mod-11 público y documentado que usa
AFIP/ARCA para el dígito verificador del CUIT/CUIL — **no** consulta ningún padrón real (confirmado
por grep: 0 referencias a `afip`/`padron`/`constancia`/`arca.gob` en todo `routes/auth.js`). Se
generaron **200 CUITs** en memoria (prefijos de persona física 20/23/24/27 y jurídica 30/33/34 +
secuencia + checksum calculado con la misma fórmula) y **los 200 pasan** la validación real del
backend — confirma que el único freno efectivo contra reuso es la `UNIQUE` de la base
(`users_cuit_unique`), no la validación de formato. Generar CUITs sintácticamente válidos en volumen
es trivial y no requiere ningún dato real de una persona o empresa existente.

### 3.2 `registerLimiter` — confirmado en vivo, no asumido

`middleware/rateLimiter.js:24-41` (3 registros / hora, por IP vía `express-rate-limit` con
`trust proxy: 1`, `server.js:139`). Se corrieron **4 registros reales** contra
`POST /auth/register` desde el mismo origen: los primeros 3 dieron `201` (registro real creado,
verificación enviada), el 4to dio **`429`** con `action:'wait'` — el rate limit está vivo y funciona
como está documentado.

### 3.3 🚨 AUTH-1/`machine_id` no limita el farmeo — es anti-robo-de-token, no anti-multi-cuenta

Se crearon 2 cuentas fixture (A y B), ambas con suscripción `active` y trial disponible, y se les
asignó el **mismo** `machine_id` simulado (representando 2 cuentas registradas desde la misma PC).
Se llamó `POST /license/execution/start` para las dos, con el mismo `machineId`, en el mismo
instante:

| Llamada | Resultado |
|---|---|
| Cuenta A arranca ejecución | `200` |
| Cuenta B, mismo `machineId`, mismo momento | `200` (sin ningún rechazo ni demora agregada) |
| `active_executions` con ese `machine_id` | 2 filas simultáneas confirmadas por consulta directa |

Confirma con evidencia lo que el código ya sugería (`routes/license.js:73-86`, el `ON CONFLICT
(user_id)` del lock es por **usuario**, no por `machine_id` — no hay ninguna restricción de unicidad
sobre `machine_id` en `users` ni un tope agregado por dispositivo en `active_executions`). **No es un
bug de AUTH-1** — el control fue diseñado y documentado explícitamente
(`routes/auth.js:611-621`, `routes/license.js:40-46`) como protección contra **reuso de un token
robado desde otro equipo**, y en eso funciona: se confirmó como no-regresión que la MISMA cuenta A,
usando un segundo `machineId` mientras su lock del primero seguía vivo, sí recibe `403
DEVICE_MISMATCH`. El punto real es que **nunca fue diseñado para limitar cuántas cuentas puede tener
un mismo dispositivo**, y hoy no lo hace en absoluto — cada cuenta nueva es 20 usos de trial gratis,
sin ningún costo de fricción por reusar la misma PC.

### 3.4 Email desechable — sin verificación de dominio, confirmado por código (sin usar un servicio real de terceros)

Siguiendo la instrucción del plan de no pegarle a un servicio externo real, se confirmó por lectura
completa de `POST /auth/register` (`routes/auth.js:111-260`) que no hay ninguna verificación de
dominio de email (ni lista de bloqueo, ni consulta MX, ni servicio anti-disposable) — grep de
`disposable`/`blocklist`/`dominio.*bloque` en todo `backend-server/` da 0 coincidencias. El único
freno es que el email de verificación tiene que llegar a una casilla real para que la cuenta pase de
`pending_email` a `pending_activation` — un dominio inexistente (ej. `.invalid`, usado en la propia
prueba de 3.2) permite crear la cuenta pero la deja **atascada sin verificar**, sin acceso real (el
trial no se activa hasta verificar el email). Verificado indirectamente: los 3 registros de 3.2, con
dominio `.invalid`, quedaron en `pending_email` — confirmado por el log del propio servidor
("✅ Nuevo registro" sin ningún evento posterior de verificación). O sea que un email desechable real
(uno que sí recibe correo, tipo mailinator) sortearía esta fricción sin problema — el freno real hoy
es solo "¿el dominio recibe mail?", no "¿es un dominio legítimo/no desechable?".

### 3.5 CORS — confirmado en vivo, sigue acotado

`PUBLIC_OPEN_CORS_PATHS = ['/analytics/event']` (`server.js:84`, un solo elemento, sin cambios desde
el 2026-07-25). Confirmado con 3 requests reales, cada una con `Origin: https://evil-attacker.example`:
`POST /analytics/event` → refleja el origen (`Access-Control-Allow-Origin` = el origen enviado, por
diseño — es el único path abierto) · `POST /license/execution/start` → **no** lo refleja ·
`GET /client/account` → **no** lo refleja. El array no se ensanchó.

### 3.6 La decisión de producto — planteada, no resuelta

Con `allow_public_register=true` ya activo hoy en producción (confirmado, §0 del plan) y los 3
hallazgos de arriba (CUIT trivialmente generable, farmeo sin fricción entre cuentas de una misma PC,
email desechable sin bloqueo), el registro público abierto **regala 20 usos de automatización real
contra el PJN por cada cuenta**, sin prácticamente ningún costo para quien quiera abusarlo en volumen.
Con 3 usuarios reales hoy el riesgo es teórico; publicado, deja de serlo. **2 opciones, sin decidir:**
mantener el registro abierto (aceptando el riesgo mientras el volumen sea bajo, con la opción de
agregar fricción después — CAPTCHA, verificación de dominio de email, límite de cuentas por
`machine_id`) o pasar a lista de espera/invitación para el lanzamiento inicial. Es una palanca de
riesgo mucho más efectiva que cualquier control técnico puntual — la misma conclusión que ya
anticipaba el plan.
